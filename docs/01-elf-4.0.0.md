# Violet 4.0.0 ELF findings

Target file used during this research: `Violet4.0.0.elf` supplied by the repository owner during analysis.

## ELF identity

- Format: ELF64, little-endian, PIE, AArch64, stripped.
- GNU Build ID: `709bfd66115298640155fcc4979dba151c7cc79a`.
- `.text`: VA `0x00000000`, file offset `0x8D8`, size `0x343FC90`.
- `.rodata`: VA `0x3440000`, file offset `0x3440568`, size `0xF420A0`.
- `.data`: VA `0x4383000`, file offset `0x4382608`, size `0x368868`.
- `.bss`: VA `0x46EB868`, size `0xE7798`.

Because `.text` starts at VA 0 in this PIE image, discovered text VAs are directly useful as `main + offset` values after resolving the runtime module base.

## Native Ojama network behavior

A state dispatcher begins near `main+0xCE2584`.

At `0xCE25BC` it loads a state ID from `[x19,#4]` and dispatches values 0..11 through a jump table at rodata `0x3C3114C`.

Observed state targets:

| state | target |
|---:|---:|
| 0 | `0xCE25E0` |
| 1 | `0xCE2BC0` |
| 2 | `0xCE281C` |
| 3 | `0xCE313C` |
| 4 | `0xCE32AC` |
| 5 | `0xCE2B00` |
| 6 | `0xCE2E24` |
| 7 | `0xCE4490` |
| 8 | `0xCE2E98` |
| 9 | `0xCE37E8` |
| 10 | `0xCE4490` |
| 11 | `0xCE32F4` |

State 9 includes:

```asm
CE37E8  mov  x0, x19
CE37EC  bl   0x9A1BC4
CE37F0  adrp x1, 0x3BA6000
CE37F4  add  x1, x1, #0x4E2
CE37F8  mov  x0, x19
CE37FC  bl   0x176AD1C
```

The referenced string is `main.field.behaviour.network.ActOjamaPokemonBehavior`.

Related action/effect strings around this behavior include `FollowEscapeEffect`, `FollowEatEffect`, `eff_overhead01`, `eff_mouth01`, plus other field-network behaviors such as `FieldPokemonRecvHitForNetwork` and `PartnerPokemonRecvHit`.

### Object layout hints

The behavior object appears to contain at least:

- `+0x04` — state ID.
- `+0x28` — managed/reference pointer-like field.
- `+0x78`, `+0xB8` — helper structures/containers.
- `+0x100`, `+0x101`, `+0x102` — byte flags; `+0x102` is set to 1 during setup.

`main+0x10B05AC` builds an approximately `0x110`-byte object with compatible fields and also references both Ojama particle assets. This strongly associates the native area with Ojama field/network behavior rather than fruit accounting.

## What the ELF did *not* contain

The following high-level names were not present as normal strings in the stripped 4.0.0 ELF:

- `OniballoonAppliSceneManager`
- `OniballoonHudModel`
- `FruitsViewSupporter`
- `OnReceiveGetKinomi`
- `OnRecieveOblation`
- `IsClearColor`

This is the key reason the project moved away from trying to identify three standalone native functions named “AddFruit / Oblation / CheckRoundComplete”. Those behaviors are represented in the generated Lua/Haxe script layer. Native `main+offset` work remains valuable for runtime/network/field bridges, but is no longer the shortest implementation route for the requested automation.

## Caution

NOPing or short-circuiting `ActOjamaPokemonBehavior` is not equivalent to a clean “disable Ojama” mod. It is a network field behavior and may desynchronize participants. If disabling Ojama is desired, data/parameter-layer spawn-rate changes are preferable to destroying this native behavior state machine.
